PX4 Flight Controller Threading

A study note for the Nucleo H753ZI PX4 checkout: how modules start, when PX4 creates normal tasks, and how work-queue modules share execution threads.

Startup Path Dedicated Threads Work Queues Blocking Choosing Inspecting Runtime
Dedicated task/thread Created with px4_task_spawn_cmd(). The module owns a scheduler context, stack, priority, and usually a blocking or polling loop.
Work queue item Created as a WorkItem or ScheduledWorkItem. The module runs short Run() callbacks on a shared queue thread.

Startup Path

Most PX4 modules are started from an init script or shell command. The shared ModuleBase code dispatches the command, but each module's own task_spawn() decides how execution is created.

Module start command dispatch

For work-queue modules, init() is a module convention, not a base-class virtual function. The module's own task_spawn() calls it after constructing the object.

Dedicated Thread Approach

A dedicated-thread module creates an OS scheduling context with px4_task_spawn_cmd(). This is suitable for blocking loops, px4_poll(), serial I/O, long-latency work, or code that should not delay unrelated modules.

Dedicated task lifecycle

int MyModule::task_spawn(int argc, char *argv[])
{
    desc.task_id = px4_task_spawn_cmd("my_module",
                                      SCHED_DEFAULT,
                                      SCHED_PRIORITY_DEFAULT,
                                      1200,
                                      (px4_main_t)&run_trampoline,
                                      (char *const *)argv);

    return desc.task_id < 0 ? -errno : 0;
}

Work Queue Approach

A work-queue module does not create a private thread. It attaches a WorkItem to a named queue. The work queue manager lazily creates the queue's backing thread if it does not already exist.

One queue thread, many work items

class MyWorkItem : public ModuleBase, public px4::ScheduledWorkItem
{
public:
    MyWorkItem() :
        ScheduledWorkItem("my_work_item", px4::wq_configurations::hp_default)
    {}

    bool init()
    {
        ScheduleOnInterval(10_ms);
        return true;
    }

private:
    void Run() override
    {
        // Do one bounded unit of work and return.
    }
};

Run-to-Completion and Blocking

Run() is run-to-completion with respect to its queue. PX4 will not run another item on the same queue until the current item returns. The OS can still preempt the queue thread with interrupts or higher-priority tasks.

Same queue: serial execution

A work item can technically block because it is ordinary C++ running in an OS thread. In normal flight-control code it should not block, because every other item on the same queue waits behind it.

Run() does not have its own private stack. It runs on the queue thread's stack. Local variables disappear when Run() returns; persistent state should live in member variables.

void MyController::Run()
{
    float error = compute_error();  // temporary stack variable
    _integrator += error * _dt;     // persistent object member
    publish_output(_integrator);
}

Choosing the Execution Model

Need Prefer Reason
Short periodic control update Work queue Lower thread count and predictable callback runtime.
React to uORB publication Work queue uORB callback subscriptions can enqueue Run() directly.
Blocking px4_poll(), serial read, file I/O, or sleep loop Dedicated thread Blocking one module should not stall unrelated work items.
Long or variable-latency computation Dedicated thread The module gets an independent scheduler context and stack.
High-rate control with bounded work Work queue PX4 commonly uses queues such as wq:rate_ctrl for this path.

Inspecting Runtime

Use these commands on a running PX4 target:

top
work_queue status
<module> status
  • top shows OS tasks and threads, including dedicated module tasks and active work queue threads.
  • work_queue status shows the active PX4 queues and attached work items.
  • <module> status shows module-specific status output.

The total task/thread count is target- and runtime-dependent. Startup parameters, active sensors, MAVLink links, and simulation mode can change which dedicated tasks and queue threads exist.
