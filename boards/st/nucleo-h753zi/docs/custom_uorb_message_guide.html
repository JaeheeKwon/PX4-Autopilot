Concept

uORB is PX4's publish/subscribe middleware. A driver, module, or app publishes structured data to a topic, and another driver, module, or app subscribes to that topic without needing to know which hardware device or thread produced it.

1. Message File msg/MyBoardStatus.msg defines fields and optional topic aliases.
2. Code Generation Build creates uORB/topics/my_board_status.h and topic metadata.
3. Publisher Driver or module fills my_board_status_s and publishes.
4. uORB Topic PX4 stores the latest sample, queue, or multi-instance topic data.
5. Subscriber Application copies the topic and consumes the data contract.
Board bring-up implication Use uORB as the boundary between hardware-specific drivers and PX4 applications. If the lower driver is disabled for HITL or simulation, a simulator publisher can provide the same topic and the application logic can stay mostly unchanged.
Layer Responsibility Example
Hardware / board Capture physical data from GPIO, SPI, I2C, UART, ADC, PWM capture, or interrupts. Board status, custom sensor, external safety monitor.
Driver Convert hardware-specific data into a PX4 message contract. Publish my_board_status or an existing standard topic.
uORB Transport typed data between threads/modules with timestamps, queueing, and optional multi-instance support. ORB_ID(my_board_status).
Application Subscribe to the topic and implement behavior without depending on the lower hardware driver. Health monitor, controller, logger, command handler.

Build Flow

PX4 message generation is integrated into the normal CMake build. Adding a .msg file is not enough in this checkout: the file must also be listed in msg/CMakeLists.txt. 

msg/MyBoardStatus.msg
  -> listed in msg/CMakeLists.txt
  -> Tools/msg/px_generate_uorb_topic_files.py runs during build
  -> build/<target>/uORB/topics/my_board_status.h
  -> build/<target>/msg/topics_sources/my_board_status.cpp
  -> application includes <uORB/topics/my_board_status.h>
  -> publisher/subscriber use ORB_ID(my_board_status)

Message Design

A uORB message is a software interface contract. Treat it like an API: name it for the data it represents, document units, avoid leaking bus-specific details, and keep timestamps explicit.

Recommended Message for a Custom Board Status Topic

# Custom board status reported by the board support layer or health driver.

uint64 timestamp        # [us] Time since system start when this message is published.
uint64 timestamp_sample # [us] Time when the raw hardware state was sampled.

uint8 STATE_UNKNOWN = 0
uint8 STATE_OK = 1
uint8 STATE_WARNING = 2
uint8 STATE_ERROR = 3

uint8 state             # Current board state.
float32 temperature_c   # [deg C] Board or MCU temperature if available, NAN otherwise.
float32 supply_v        # [V] Board supply voltage if available, NAN otherwise.
uint32 error_count      # Monotonic count of detected hardware or communication errors.

Save this as msg/MyBoardStatus.msg. PX4 converts CamelCase file names to snake_case topic names, so MyBoardStatus.msg becomes my_board_status.

Rule Reason Example
Always include uint64 timestamp PX4 logging and tooling expect timestamped topics. msg.timestamp = hrt_absolute_time();
Use timestamp_sample for sensor-like data Separates raw capture time from publication time. IRQ timestamp or ADC conversion completion time.
Document units in comments Generated docs and logs become understandable. float32 supply_v # [V]
Avoid protocol-specific fields Apps should not care whether data came from SPI, I2C, UART, HITL, or simulation. Use error_count, not raw register dump fields, unless needed.
Use fixed-size arrays only when needed Messages have fixed binary layouts and are logged. float32[3] xyz

Multi-Topic Message

If two topic names share the exact same payload, add # TOPICS at the end of the message. 

# TOPICS my_board_status my_board_status_sim

This creates two distinct topics with the same message layout. This is different from multi-instance publishing, where one topic has several instances, such as multiple sensors of the same type.

Queue Length

uORB defaults to keeping the latest sample. For command/event data where drops matter, define an explicit queue length. The queue length must be a power of two. 

uint8 ORB_QUEUE_LENGTH = 4
Use queues sparingly A status or sensor topic usually only needs the latest value. A command, request, acknowledgement, or event topic may need a queue to avoid losing bursts.

Add the Message to PX4

  1. Create msg/MyBoardStatus.msg.
  2. Add MyBoardStatus.msg to the msg_files list in msg/CMakeLists.txt.
  3. Include the generated header from publisher and subscriber code.
  4. Enable the module or driver that uses it in the board .px4board file.
  5. Build the target so PX4 regenerates uORB headers and topic metadata.

CMake Change

set(msg_files
    ...
    MyBoardStatus.msg
    ...
)

#include <uORB/topics/my_board_status.h>

Publish From a Driver or Module

The C++ API is the preferred style for most modern PX4 modules and drivers. A publication object is normally a class member, and the driver publishes each time it has a fresh sample.

Header Member

#include <uORB/Publication.hpp>
#include <uORB/topics/my_board_status.h>

class MyBoardMonitor
{
public:
    void publish_status();

private:
    uORB::Publication<my_board_status_s> _status_pub{ORB_ID(my_board_status)};
    uint32_t _error_count{0};
};

Publisher Implementation

#include <drivers/drv_hrt.h>
#include <mathlib/mathlib.h>

void MyBoardMonitor::publish_status()
{
    const hrt_abstime sample_time = hrt_absolute_time();

    my_board_status_s status{};
    status.timestamp_sample = sample_time;
    status.timestamp = hrt_absolute_time();
    status.state = my_board_status_s::STATE_OK;
    status.temperature_c = NAN;
    status.supply_v = 5.0f;
    status.error_count = _error_count;

    _status_pub.publish(status);
}

Where This Fits in a Driver

Polling / IRQ Driver gets raw hardware sample or event.
Decode Convert registers, bytes, ADC values, or GPIO state.
Timestamp Set timestamp_sample and timestamp.
Publish _status_pub.publish(status).
Consumers App, logger, health monitor, or HITL replacement.
Interrupt context caution uORB can be used from interrupt-related contexts, but the topic must be advertised and published once outside the interrupt context first. The normal PX4 driver pattern is to capture the IRQ timestamp, schedule work, and publish from the work queue.

C API Publisher

Older code can use the C API directly. 

#include <uORB/uORB.h>
#include <uORB/topics/my_board_status.h>

struct my_board_status_s status = {};
status.timestamp = hrt_absolute_time();

orb_advert_t pub = orb_advertise(ORB_ID(my_board_status), &status);

status.state = my_board_status_s::STATE_OK;
status.timestamp = hrt_absolute_time();
orb_publish(ORB_ID(my_board_status), pub, &status);

Subscribe From an Application

Applications can subscribe without knowing which hardware driver produced the data. This is the abstraction that makes it possible to disable a lower driver in HITL and replace it with a simulator publisher.

Simple C++ Subscription

#include <uORB/Subscription.hpp>
#include <uORB/topics/my_board_status.h>

class MyBoardConsumer
{
public:
    void update();

private:
    uORB::Subscription _status_sub{ORB_ID(my_board_status)};
    my_board_status_s _last_status{};
};

void MyBoardConsumer::update()
{
    if (_status_sub.updated()) {
        my_board_status_s status{};

        if (_status_sub.copy(&status)) {
            _last_status = status;

            if (status.state == my_board_status_s::STATE_ERROR) {
                // Take application-specific action.
            }
        }
    }
}

Callback Work Item Subscription

If the module should run whenever the topic updates, use SubscriptionCallbackWorkItem. This is common for work-queue based modules. 

#include <px4_platform_common/px4_work_queue/ScheduledWorkItem.hpp>
#include <uORB/SubscriptionCallback.hpp>
#include <uORB/topics/my_board_status.h>

class MyBoardConsumer :
    public px4::ScheduledWorkItem
{
public:
    bool init()
    {
        return _status_sub.registerCallback();
    }

private:
    void Run() override
    {
        my_board_status_s status{};

        while (_status_sub.update(&status)) {
            // Consume every available update from this callback.
        }
    }

    uORB::SubscriptionCallbackWorkItem _status_sub{this, ORB_ID(my_board_status)};
};

C API Subscriber

#include <poll.h>
#include <px4_platform_common/posix.h>
#include <uORB/uORB.h>
#include <uORB/topics/my_board_status.h>

int sub = orb_subscribe(ORB_ID(my_board_status));
orb_set_interval(sub, 200); // Limit updates to 5 Hz.

px4_pollfd_struct_t fds[] = {
    { .fd = sub, .events = POLLIN },
};

if (px4_poll(fds, 1, 1000) > 0 && (fds[0].revents & POLLIN)) {
    struct my_board_status_s status;
    orb_copy(ORB_ID(my_board_status), sub, &status);
}

Logging and DDS Exposure

Defining a uORB topic makes it available inside PX4. It does not automatically mean that the topic is logged by default or bridged to ROS 2/DDS.

ULog logging To include the topic in default logs, add it to src/modules/logger/logged_topics.cpp, or use a runtime logger_topics.txt file if that is more appropriate for experiments.
ROS 2 / uXRCE-DDS To expose the topic externally, add it to src/modules/uxrce_dds_client/dds_topics.yaml and make sure the matching message definition exists in the external px4_msgs workspace.

Logger Example

// src/modules/logger/logged_topics.cpp
add_optional_topic("my_board_status", 100); // minimum interval in ms

DDS Topic Selection

Add the custom topic to the DDS topic configuration only if a companion computer or ROS 2 node needs it. If it is only internal to PX4, keep it internal to reduce ABI and compatibility burden.

Versioned messages If the message is exposed to ROS 2 and must remain compatible across PX4/ROS versions, place it under msg/versioned and include uint32 MESSAGE_VERSION = 0. Updating versioned messages has additional migration requirements.

Build and Test

After adding the message and publisher/subscriber code, build the board target so PX4 regenerates topic headers and validates that all code includes match the generated names.

Check Expected Result If It Fails
Build finds my_board_status.h Generated header exists under the build directory. Confirm MyBoardStatus.msg is listed in msg/CMakeLists.txt.
listener my_board_status 5 Five messages print with timestamps and field values. Confirm publisher module is running and topic name matches snake_case conversion.
uorb top Topic appears with publication rate, subscriber count, queue size, and lost count. Confirm the board build includes the publisher and uORB command support.
ULog contains topic Topic appears in log analysis tools. Add topic to logger defaults or runtime logger topic config.

Patterns and Pitfalls

Good Patterns

  • Use existing standard PX4 messages if they already match the semantic meaning.
  • Create a custom message only when the data is a new software contract.
  • Keep bus details below the uORB boundary.
  • Set timestamp_sample from the data capture time.
  • Set timestamp at publication time.
  • Use PublicationMulti for several devices of the same type.
  • Use # TOPICS for several named topics sharing one structure.
  • Use SubscriptionInterval when consumers do not need every update.
  • Add logger support only when the topic is needed in evidence, debug, or analysis logs.
  • Add DDS support only when a companion-side consumer needs the topic.

Common Pitfalls

Pitfall Consequence Correction
Adding .msg but not editing msg/CMakeLists.txt No generated header; include fails. Add the message to msg_files.
Using wrong generated include name Compiler cannot find the header. Convert CamelCase file name to snake_case include name.
Forgetting timestamp Logging and tooling behavior is poor or invalid. Always include and fill uint64 timestamp.
Encoding hardware registers as app-level API Application becomes tied to one device implementation. Publish semantic state, units, health, and values instead.
Using queue length for high-rate sensor streams without need Extra memory and possible stale backlog. Use latest-sample semantics unless every message matters.
Publishing from IRQ before advertisement Runtime failure or undefined behavior. Advertise/publish once from normal context, then use scheduled work for IRQ-driven drivers.
Changing an existing message without compatibility review Breaks logs, Flight Review, ROS 2, or external tooling. Add a new field, deprecate old fields carefully, or use versioned messages.

Decision Guide

Need Recommended Approach
New physical sensor already represented by PX4 Publish the existing standard topic, such as sensor_accel, distance_sensor, or sensor_baro.
Board health or custom safety monitor Create a custom board status topic.
Simulation replacement for a driver Publish the same uORB topic from a simulator/HITL module and disable the real hardware driver.
Multiple identical devices Use multi-instance publication/subscription.
Multiple logical channels with same data layout Use # TOPICS topic_a topic_b.
External ROS 2 consumer Consider a versioned message and add DDS topic configuration.
