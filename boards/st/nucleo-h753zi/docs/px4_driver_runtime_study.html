PX4 Driver Study

Runtime Abstraction, uORB Publication, HITL Replacement, and Driver Rates

This study explains how PX4 input and output drivers behave at runtime, how input drivers publish through uORB, how hardware drivers can be replaced by HITL or simulation publishers, and where driver update rates are specified.

Executive Summary

Main Finding

PX4 drivers hide device-specific data generation details behind a typed uORB message contract. A consumer usually subscribes to a topic such as distance_sensor, sensor_gyro, sensor_accel, or sensor_gps rather than calling a physical driver directly.

Architecture Benefit

Because the application consumes uORB topics, the underlying producer can be a real hardware driver, a simulator, a HITL bridge, a replay source, or a test stub. The application code does not need to distinguish the source if the topic contract and timing semantics are preserved.

Short conclusion

PX4 does not impose one universal hardware data generation model. Some devices are scheduled/polled, some are interrupt driven, some read streaming serial data, and output drivers are driven by actuator/control topic updates plus hardware timer configuration. The common abstraction is the driver module plus uORB topic boundary.

Driver Implementation Pattern

PX4 driver code follows a consistent implementation style even though individual devices use different buses, sample timing, and protocols. A driver is usually a runtime module with an explicit lifecycle, a bus or output abstraction, scheduled execution, uORB publication/subscription, and built-in diagnostics.

Pattern Element Typical PX4 Implementation Purpose Example
Build/module declaration px4_add_module() with MODULE, MAIN, SRCS, and DEPENDS Compiles each driver as an independently startable PX4 module. drivers__distance_sensor__srf02, drivers__pwm_out
Runtime entry point extern "C" __EXPORT int *_main(int argc, char *argv[]) or ModuleBase descriptor Provides CLI lifecycle commands and module startup. srf02_main(), PWMOut::task_spawn()
Common lifecycle verbs start, stop, status Allows runtime control and inspection without application coupling. I2CSPIDriver::module_start(), module_stop(), module_status()
I2C/SPI bus abstraction device::I2C or SPI base class plus I2CSPIDriver<T> Centralizes bus selection, device ID, instance management, and work queue setup. class SRF02 : public device::I2C, public I2CSPIDriver<SRF02>
Scheduled execution px4::ScheduledWorkItem, Run(), or RunImpl() Keeps hardware IO bounded and avoids direct blocking from consumers. SRF02::RunImpl(), BMI270::RunImpl(), PWMOut::Run()
Sensor wrapper PX4Rangefinder, PX4Accelerometer, PX4Gyroscope, and similar wrappers Normalizes fields, device identity, orientation, and uORB publication. _px4_rangefinder.update(...)
Output mediation ModuleBase plus OutputModuleInterface and MixingOutput Separates actuator intent, output assignment, limiting, and physical writes. PWMOut
Diagnostics perf_alloc, perf_count, perf_print_counter, print_status() Exposes timing, interval, communication errors, and runtime health. _sample_perf, _comms_errors, _interval_perf

Input Sensor Skeleton

class MySensor final : public device::I2C, public I2CSPIDriver<MySensor>
{
public:
  int init() override
  {
    if (I2C::init() != PX4_OK) {
      return PX4_ERROR;
    }

    ScheduleDelayed(first_cycle_delay_us);
    return PX4_OK;
  }

  void RunImpl()
  {
    const hrt_abstime timestamp_sample = hrt_absolute_time();

    if (read_device_and_convert() == PX4_OK) {
      _sensor_wrapper.update(timestamp_sample, normalized_value);
    } else {
      perf_count(_comms_errors);
    }

    ScheduleDelayed(sample_interval_us);
  }
};

Output Driver Skeleton

class MyOutput final : public ModuleBase, public OutputModuleInterface
{
private:
  void Run() override
  {
    if (should_exit()) {
      ScheduleClear();
      exit_and_cleanup(desc);
      return;
    }

    _mixing_output.update();
    check_parameter_updates();
    _mixing_output.updateSubscriptions(true);
  }

  bool updateOutputs(float outputs[MAX_ACTUATORS],
                     unsigned num_outputs,
                     unsigned num_control_groups_updated) override
  {
    for (unsigned i = 0; i < num_outputs; ++i) {
      write_output_channel(i, outputs[i]);
    }

    trigger_hardware_update(num_control_groups_updated);
    return true;
  }
};

Implementation pattern takeaway

The driver implementation pattern is not just "read hardware and publish." A PX4 driver is a managed module: it owns startup, bus/device selection, scheduling, protocol handling, normalization, publication or output writes, parameters, and runtime diagnostics.

uORB Boundary

Input drivers normally publish data to uORB. The driver owns hardware access, sample timing, data conversion, device identity, and health counters. Consumers subscribe to the normalized topic and use timestamps and metadata to judge freshness and validity.

SRF02 Example

The SRF02 rangefinder reads two I2C bytes, converts the result from centimeters to meters, and calls the rangefinder wrapper: 

_px4_rangefinder.update(timestamp_sample, distance_m);

The wrapper publishes a distance_sensor_s uORB message. That means the estimator or control code does not need to know about SRF02 I2C commands or conversion timing.

HITL And Simulation Replacement

Since the application layer subscribes to uORB topics, a physical input driver can be disabled for HITL or simulation and replaced by another publisher that emits the same message type. This is the key abstraction property.

Important nuance

A replacement publisher must mimic more than message fields. For realistic HITL, it should preserve update rate, timestamps, jitter, freshness behavior, device identity where relevant, batching/FIFO behavior, fault injection, stale data behavior, and validity flags. Otherwise the application will subscribe successfully but may behave differently.

Hardware Data Generation Patterns

Different hardware devices generate data differently. PX4 keeps those details inside the driver while exposing a consistent uORB-facing interface.

Generation Pattern PX4 Mechanism Example uORB Effect
Scheduled polling ScheduleOnInterval() or ScheduleDelayed() SRF02 rangefinder Publishes one sample per measurement cycle.
Command, wait, collect Driver state machine in RunImpl() Many rangefinders Publishes after conversion time completes.
Data-ready interrupt GPIO event calls callback, then ScheduleNow() BMI270 IMU Work queue reads FIFO/sample near hardware-ready time.
FIFO batching Read multiple samples per work item and publish FIFO topic Modern IMUs Preserves high-rate data without one work item per sample.
Streaming serial poll(), read(), protocol parser GPS and serial rangefinders Publishes when a complete valid frame is decoded.
Actuator output uORB callbacks, mixer update, board output API PWMOut Consumes actuator topics and writes physical outputs.

How Driver Rates Are Specified

There is no single universal rate specification mechanism across all PX4 drivers. The rate may be hard-coded, computed from hardware configuration, set by a PX4 parameter, controlled by an output timer group, or adjusted downstream by a consumer.

Rate Type Where Specified Example How To Change Risk/Note
Hard-coded polling/conversion interval Driver header/source constant SRF02_CONVERSION_INTERVAL Code change, or add a PX4 parameter Must respect sensor conversion time and acoustic/physical interference.
Device register sample rate Driver configuration code BMI270::RATE and FIFO watermark Code/device configuration change Must match filter assumptions, FIFO capacity, bus bandwidth, and CPU budget.
Driver parameter PX4 parameter YAML and driver read path GPS_UBX_RATE Set PX4 parameter and reboot if required Device model and baudrate may limit practical rate.
Output hardware timer rate Output module parameter PWM_MAIN_TIMx / PWM_AUX_TIMx Set output timer parameter Timer groups share rates; ESC/servo protocol limits apply.
Downstream processing/integration rate Consumer module parameter IMU_INTEG_RATE Set consumer parameter Does not necessarily change raw hardware sampling rate.
Topic callback or fixed scheduling rate Middleware subscription and scheduler logic MixingOutput scheduling policy Module/framework configuration Rate may be driven by topic updates rather than a fixed loop.

Terminology caution

"Driver rate" can mean hardware sample rate, FIFO transfer rate, uORB publication rate, actuator output update rate, or consumer processing rate. These are related but not identical. A design review should name which rate is being changed.

Concrete PX4 Examples

1. SRF02 Rangefinder: Hard-Coded Scheduled Input

SRF02 has a compile-time interval and a simple state machine. It starts a measurement, waits for conversion, collects the result, converts it, and publishes. 

#define SRF02_CONVERSION_INTERVAL 100000
int _interval{SRF02_CONVERSION_INTERVAL};

void SRF02::RunImpl()
{
  if (_collect_phase) {
    collect();
    _collect_phase = false;
  }

  measure();
  _collect_phase = true;
  ScheduleDelayed(_interval);
}

2. BMI270 IMU: Device Rate, FIFO, IRQ, And Fallback

BMI270 uses a hardware sample rate constant and FIFO batching. If the data-ready interrupt is configured successfully, the interrupt schedules the work item. If not, the driver falls back to periodic scheduling based on the FIFO empty interval. 

static constexpr uint32_t RATE{1600}; // 1600 Hz
static constexpr float FIFO_SAMPLE_DT{1e6f / RATE};

if (DataReadyInterruptConfigure()) {
  _data_ready_interrupt_enabled = true;
  ScheduleDelayed(100_ms); // watchdog backup
} else {
  ScheduleOnInterval(_fifo_empty_interval_us, _fifo_empty_interval_us);
}

3. GPS: Parameterized Device Output Rate

The GPS driver exposes GPS_UBX_RATE as a parameter. The driver reads it and passes the desired output rate into the u-blox device configuration path. The final effective rate depends on the receiver model, RTK mode, baudrate, and configured messages. 

GPS_UBX_RATE:
  short: u-blox GPS output rate
  default: 0
  min: 0
  max: 25

4. PWMOut: Output Timer Rate Parameters

PWMOut gets timer rates from output parameters such as PWM_MAIN_TIMx or PWM_AUX_TIMx. A positive value configures PWM frequency. Negative values select protocols such as OneShot or DShot variants. 

snprintf(param_name, sizeof(param_name), "%s_TIM%u",
         _mixing_output.paramPrefix(), timer);

param_get(handle, &tim_config);

if (tim_config > 0) {
  _timer_rates[timer] = tim_config;
} else if (tim_config == -1) {
  _timer_rates[timer] = 0; // OneShot
}

5. VehicleIMU: Consumer Integration Rate

IMU_INTEG_RATE controls downstream IMU integration behavior in the sensor module. It is not necessarily the raw IMU hardware sample rate. 

const int32_t imu_integration_rate_hz =
  constrain(_param_imu_integ_rate.get(), 50, 1000);

_imu_integration_interval_us = 1e6f / imu_integration_rate_hz;

Implications For Self-Driving Software

The PX4 pattern is directly useful for a self-driving platform if adapted carefully. The core idea is to isolate physical devices behind stable message contracts while keeping source timing, health, and failure behavior explicit.

PX4 Lesson Automotive Application Design Rule
Consumers subscribe to uORB, not drivers. Perception/control subscribe to DDS/ROS 2/vehicle middleware topics. Do not let algorithms depend on hardware-driver APIs.
Driver timing model is private to the driver. Radar, lidar, ultrasonic, IMU, and CAN devices can use different acquisition models. Normalize into a topic with timestamp, frame, source ID, and health.
HITL can replace hardware behind the same topic. Vehicle bench, replay, and simulation can publish the same interface. Simulated publishers must mimic timing and failure semantics, not just data fields.
Rates are layered and source-specific. Camera frame rate, lidar spin rate, radar cycle time, CAN command period, and fusion rate differ. Document hardware rate, publication rate, and consumer processing rate separately.
Output drivers mediate final actuation. Steering, brake, throttle, and gear commands should pass through arbitration and limiting. Keep physical actuation behind a bounded output layer with safe states.

Safety note

For a safety-relevant self-driving system, this architecture needs additional evidence: requirements traceability, timing budgets, stale-data handling, source selection rules, diagnostic coverage, fault injection results, ISO 26262 safety analysis, and cybersecurity controls for update, debug, and configuration paths.

Driver Study Checklist

Question What To Capture Why It Matters
What topic does the driver publish or consume? uORB topic name, message fields, instance behavior. Defines the replacement contract for simulation and HITL.
What generates data? Polling, command/wait/collect, IRQ, FIFO, serial stream, callback. Determines realistic timing and fault modeling.
Where is the rate configured? Code constant, parameter, device register, timer group, consumer parameter. Avoids changing the wrong rate layer.
What metadata is required? Timestamp, device ID, orientation/frame, calibration link, quality/validity. Prevents source ambiguity and stale-data misuse.
How is health exposed? Communication errors, perf counters, status print, timeout behavior. Supports diagnosis, failover, and serviceability.
Can the hardware driver be disabled? Startup script/module config and replacement publisher plan. Enables HITL and simulation without application changes.
What happens on invalid or missing data? Timeouts, stale flags, fallback source selection, safe output state. Critical for safety-relevant runtime behavior.
