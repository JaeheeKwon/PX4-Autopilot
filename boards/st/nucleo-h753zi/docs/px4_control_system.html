PX4 Control System Architecture

This document explains the PX4 control path from sensors to actuators, with emphasis on the default multicopter cascaded controller. It also maps the controller blocks to implementation files, uORB topics, and key tuning parameters in this checkout.

Scope: PX4 controllers Primary path: multicopter Related: EKF2 equations

1. Summary

PX4's default multicopter controller is not model predictive control. The name MPC_* in many PX4 parameters means Multicopter Position Control, not Model Predictive Control. The default control structure is a fast cascaded controller:

position P -> velocity PID -> acceleration/thrust mapping -> attitude P -> rate PID -> control allocation

The controller is split across modules. State estimation produces attitude, velocity, and position. Flight mode logic produces trajectory setpoints. Control modules convert those setpoints into thrust and torque demands. The control allocator converts thrust and torque into motor and servo commands.

Important distinction: PX4 does contain optimization-like allocation methods such as pseudo-inverse allocation and sequential desaturation, but the default multicopter flight controller is not solving a finite-horizon model-predictive optimization problem every cycle.

3. Vehicle Model Dependency

The PX4 controller is not fully independent from the vehicle model. PX4 shares the same high-level architecture across vehicles, but the actual control law and actuator mapping are vehicle-specific. A multicopter, fixed-wing aircraft, Ackermann rover, differential rover, and mecanum rover do not use the same controller.

common architecture = sensors + EKF2 + commander + modes + uORB + actuator outputs
vehicle-specific part = controller module + actuator mapping + geometry parameters

For a Land Rover style platform, the closest PX4 vehicle class is an Ackermann rover: one forward/reverse throttle output and one steering output. PX4 routes manual, mission, or offboard commands into rover setpoints, then the Ackermann controller converts those setpoints into throttle and steering. 

manual / mission / offboard command
  -> rover position, speed, yaw, and yaw-rate setpoints
  -> rover_ackermann controller stack
  -> rover_throttle_setpoint + rover_steering_setpoint
  -> actuator_motors.control[0] + actuator_servos.control[0]

4. Controller Internals

The multicopter controller uses nested loops. Outer loops run on position/velocity information. Inner loops run on attitude and gyro-rate information. Inner loops are faster and closer to the actuators.

Position and velocity feedback close the outer loop through EKF2 local position. Attitude and gyro-rate feedback close the inner loop through EKF2 attitude and angular velocity. Allocator saturation feedback protects the rate-loop integrator during actuator limits.

Outer Loop

The outer loop handles position and velocity tracking. It is most affected by GNSS, optical flow, visual odometry, barometer, range sensors, and EKF2 local-position quality.

Inner Loop

The inner loop handles attitude and angular-rate tracking. It is most affected by gyro quality, frame dynamics, actuator latency, control allocation, and rate-controller tuning.

5. Control Equations

These equations are simplified representations of the implementation. They show the data flow without every limiter, failsafe, saturation, takeoff ramp, NaN setpoint rule, or filter.

Position to velocity

v_sp = v_ff + K_pos_p * (p_sp - p)

PX4 applies a proportional position controller. The result is constrained by velocity limits and combined with feed-forward velocity when provided.

Velocity to acceleration

a_sp = a_ff + K_vel_p * (v_sp - v) + I_vel - K_vel_d * v_dot
I_vel[k+1] = I_vel[k] + K_vel_i * (v_sp - v) * dt

The velocity loop is PID-style. PX4 includes anti-windup and saturation handling so the integrator does not keep pushing into actuator limits.

Acceleration to thrust and attitude

body_z_sp = normalize([-a_sp,x, -a_sp,y, g - a_sp,z])
thrust_sp = body_z_sp * collective_thrust

The acceleration demand becomes a desired thrust direction. PX4 limits tilt and maps acceleration to normalized collective thrust using the hover-thrust estimate.

Attitude to body-rate setpoint

q_error = inverse(q) * q_desired
e_q = 2 * imag(canonical(q_error))
omega_sp = K_att_p * e_q + yaw_rate_ff

The attitude loop uses quaternion error. Roll and pitch are prioritized over yaw using the yaw-weight logic.

Body-rate to torque

tau_sp = K_rate_p * (omega_sp - omega) + I_rate - K_rate_d * angular_accel + K_rate_ff * omega_sp

The rate loop is the innermost multicopter feedback loop. It consumes gyro angular velocity and angular acceleration, then produces body torque setpoints.

Torque and thrust to actuators

u = allocate(tau_sp, thrust_sp, actuator_effectiveness, constraints)

The allocator maps desired force and moment into actuator commands. Depending on the configured method, it uses pseudo-inverse allocation with clipping or sequential desaturation.

8. uORB Topic Flow

The controller modules communicate through uORB topics. This topic-level view is useful when debugging logs or tracing data through PX4. 

sensor_accel / sensor_gyro / sensor_baro / sensor_gps / sensor_mag
  -> sensors
  -> sensor_combined, vehicle_imu
  -> ekf2
  -> vehicle_attitude, vehicle_local_position, vehicle_global_position

manual_control_setpoint / mission / offboard setpoints
  -> commander, navigator, flight_mode_manager
  -> vehicle_control_mode, trajectory_setpoint, vehicle_constraints

vehicle_local_position + trajectory_setpoint
  -> mc_pos_control
  -> vehicle_attitude_setpoint + vehicle_local_position_setpoint

vehicle_attitude + vehicle_attitude_setpoint
  -> mc_att_control
  -> vehicle_rates_setpoint

vehicle_angular_velocity + vehicle_rates_setpoint
  -> mc_rate_control
  -> vehicle_torque_setpoint + vehicle_thrust_setpoint

vehicle_torque_setpoint + vehicle_thrust_setpoint + actuator geometry
  -> control_allocator
  -> actuator_motors + actuator_servos
  -> output driver
  -> ESCs, motors, servos

Ackermann rover command path:
manual_control_setpoint / mission / offboard setpoints
  -> rover_position_setpoint, rover_speed_setpoint, rover_attitude_setpoint, rover_rate_setpoint
  -> rover_ackermann
  -> rover_throttle_setpoint + rover_steering_setpoint
  -> actuator_motors.control[0] + actuator_servos.control[0]
  -> motor controller + steering servo

9. Ackermann Rover Build

A Land Rover style platform should normally be built as an Ackermann rover. PX4 already provides the generic Ackermann airframe 51000_generic_rover_ackermann. That airframe loads rc.rover_ackermann_defaults, which sets VEHICLE_TYPE=rover_ackermann, MAV_TYPE=10, and CA_AIRFRAME=5, then the vehicle setup starts rover_ackermann.

Use an existing rover board target

Several PX4 board configurations already include rover modules. Pick the target matching the flight controller hardware, then build the rover variant: 

make px4_fmu-v6x_rover
make px4_fmu-v5_rover
make ark_fmu-v6x_rover

Those rover board variants enable CONFIG_MODULES_ROVER_ACKERMANN, CONFIG_MODULES_ROVER_DIFFERENTIAL, and CONFIG_MODULES_ROVER_MECANUM, while disabling unused multicopter and fixed-wing controller modules to save flash and RAM.

Build a Nucleo H753ZI rover variant

In this checkout, boards/st/nucleo-h753zi/default.px4board currently enables the multicopter controller modules and does not enable CONFIG_MODULES_ROVER_ACKERMANN. For a rover build, create a dedicated board configuration such as boards/st/nucleo-h753zi/rover.px4board based on the default file, then enable the Ackermann rover module. 

# Keep the core platform, estimator, commander, navigation, IO, and sensor options from default.px4board.
CONFIG_MODULES_ROVER_ACKERMANN=y

# Optional for a Land Rover style platform if flash/RAM are tight:
CONFIG_MODULES_ROVER_DIFFERENTIAL=n
CONFIG_MODULES_ROVER_MECANUM=n
CONFIG_MODULES_MC_ATT_CONTROL=n
CONFIG_MODULES_MC_POS_CONTROL=n
CONFIG_MODULES_MC_RATE_CONTROL=n
CONFIG_MODULES_MC_HOVER_THRUST_ESTIMATOR=n

Build the new variant with: 

make st_nucleo-h753zi_rover

If you instead modify default.px4board directly, the build command remains: 

make st_nucleo-h753zi_default

Select the Ackermann airframe

After flashing, select the Generic Rover Ackermann airframe in QGroundControl, or set the airframe from the PX4 shell: 

param set SYS_AUTOSTART 51000
param save
reboot

Configure the physical vehicle

Set the geometry and motion limits before tuning controller gains: 

param set RA_WHEEL_BASE <front_to_rear_axle_distance_m>
param set RA_MAX_STR_ANG <max_steering_angle_rad>
param set RA_STR_RATE_LIM <steering_rate_limit_deg_s>
param set RO_MAX_THR_SPEED <speed_at_full_throttle_m_s>
param set RO_SPEED_LIM <max_commanded_speed_m_s>
param set RO_ACCEL_LIM <max_acceleration_m_s2>
param set RO_DECEL_LIM <max_deceleration_m_s2>
param save
Output expectation: for the Ackermann rover module in this tree, actuator_motors.control[0] is the throttle output and actuator_servos.control[0] is the steering output. The board output driver and actuator function mapping must route those logical outputs to the actual motor controller and steering servo pins.

10. Notes and Caveats

  • MPC_* parameters belong to multicopter position control. They do not imply model predictive control.
  • PX4 has multiple vehicle-specific control stacks. Multicopter, fixed-wing, VTOL, rover, UUV, and spacecraft controllers share some infrastructure but do not all use the same control law.
  • Offboard mode can bypass parts of the onboard guidance stack by sending lower-level setpoints, but the onboard attitude, rate, and allocation loops may still run depending on the selected offboard control mode.
  • The control allocator feeds saturation status back to the rate controller. That feedback is part of anti-windup behavior and is important when actuators saturate.
  • Estimator quality directly affects control quality. Position-control tuning should be evaluated together with EKF innovations, local-position validity, vibration, and sensor timing.
