Scope

This document describes the EKF2 path used by the current ST_NUCLEO_H753ZI default build. It focuses on the PX4 wrapper module in src/modules/ekf2, the sensor publication pipeline in src/modules/sensors, and the MAVLink HITL conversion path in src/modules/mavlink.

Important distinction

EKF2 does not consume MAVLink messages directly and does not read physical sensor buses directly. EKF2 consumes uORB topics. HITL and real flight differ mainly in how those uORB topics are produced.

Architecture

EKF2 is a PX4 module that wraps the ECL estimator core. The wrapper owns uORB subscriptions, parameter updates, command handling, work-queue scheduling, sensor sample conversion, publication of vehicle state topics, and estimator status topics. The core Ekf object owns the estimator state, covariance, prediction, aiding-source control, innovation checks, and output predictor.

Startup Sequence

Computation Flow

The EKF2 run loop is driven by IMU data. In multi-instance mode it subscribes to vehicle_imu; otherwise it can use sensor_combined. This board now uses the EKF selector path with SENS_IMU_MODE=0 and EKF2_MULTI_IMU=3, matching PX4's MAVLink simulator defaults.

Timestamps and Fusion Horizon

EKF2 is deliberately timestamp-driven. It does not simply fuse every observation at the moment the message is received. The estimator keeps an IMU history and runs its main fusion on a delayed time horizon so slower or delayed aiding sources can be aligned with the matching IMU state.

Why HITL can differ from a real system

HITL and real hardware can have different timestamp_sample meanings. In this Nucleo-H753ZI HITL path, most HIL_SENSOR values are timestamped when PX4 receives and decodes the MAVLink packet. In a real system, drivers often timestamp closer to the hardware sample time, FIFO sample time, interrupt time, or PPS-corrected GPS observation time. EKF2 will treat both as valid timestamps, so different timestamp semantics can shift when an observation becomes eligible for fusion.

In the ECL interface, setIMUData() pushes downsampled IMU into the IMU buffer and sets _time_delayed_us from the oldest retained IMU sample. Aiding samples are pushed into their own buffers after applying configured delays such as EKF2_MAG_DELAY, EKF2_BARO_DELAY, EKF2_OF_DELAY, and EKF2_RNG_DELAY. GPS is special: VehicleGPSPosition applies SENS_GPS0_DELAY or SENS_GPS1_DELAY to timestamp_sample if the GPS driver did not provide a corrected sample timestamp, then EKF2 buffers that GPS sample.

Expected differences

For normal Nucleo-H753ZI HITL bring-up, this timestamp difference is acceptable if the MAVLink stream is stable. The current working state proves that the estimator can align tilt, yaw, GPS position, and height and pass commander checks. However, it can still produce behavior that is not bit-for-bit equivalent to a real vehicle:

  • GPS, baro, mag, or flow innovations can differ because the observation is fused at a slightly different relative time.
  • Startup alignment timing can differ, especially yaw alignment and GPS health checks.
  • High USB/MAVLink jitter can show up as IMU interval jitter because HIL IMU sample time follows receive time.
  • Controller phase and latency can differ if the estimator output predictor is correcting for a different delay profile than real hardware.
  • Precise estimator timing validation should use synchronized simulator sample time rather than receive time.

If high-fidelity estimator timing is required, the better design is to translate simulator sample time into PX4 monotonic time using MAVLink time synchronization, then publish timestamp_sample as the simulated measurement time. That would make HIL closer to the real driver model, where sample timestamps represent when the measurement was taken rather than when the packet was received.

HITL Data Flow

In classical MAVLink HITL, the simulator sends MAVLink sensor messages over CN13 USB. mavlink_receiver decodes those messages and publishes normal PX4 sensor topics. The rest of PX4 sees normal uORB topics, except that device IDs identify simulated or MAVLink devices.

Health and Debugging

The most useful EKF2 debug topics are the sensor inputs, estimator flags, and commander preflight result. For the Nucleo HITL case, the key heading checks are vehicle_magnetometer, cs_yaw_align, cs_heading_observable, cs_mag, and commander check.
