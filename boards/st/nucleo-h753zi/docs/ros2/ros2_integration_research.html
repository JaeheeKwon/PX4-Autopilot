1. Recommended architecture

Use PX4's uxrce_dds_client on the flight controller and run MicroXRCEAgent on the ROS 2 computer. The agent is a proxy between the resource-constrained XRCE client and the host DDS/ROS 2 data space. PX4 applications do not run ROS 2 APIs: they continue to publish and subscribe through uORB.

This preserves independent DDS and MAVLink transports, so ROS 2 monitoring and HITL can operate concurrently without two protocols competing for one serial device.

2. Findings in the current checkout

  1. The DDS client is enabled. The board's default.px4board includes CONFIG_MODULES_UXRCE_DDS_CLIENT=y and maps TEL1 to /dev/ttyS1.
  2. The earlier CN10 wiring guidance is incorrect for a stock board. The firmware selects PG9/PG14 for USART6, but stock Arduino D0/D1 are PB7/PB6. PG9 and PG14 must be reached through the Morpho headers unless the firmware is changed to enable and use LPUART1 on PB6/PB7. PG14 is additionally present on Arduino D2, but PG9 is not present on Arduino D0.
  3. USART6 is enabled by NuttX. With serial reordering disabled and USART3 serving as the console, USART6 enumerates as /dev/ttyS1.
  4. Versioned messages change final DDS topic names. For example, VehicleStatus is version 4 in this branch, so the direct DDS topic is /fmu/out/vehicle_status_v4, not /fmu/out/vehicle_status.
  5. The DDS-enabled image fits. A complete target build including the USART6 hello diagnostic uses 1,348,928 bytes of the 1,441,792-byte application region (93.56%), leaving 92,864 bytes. Test-only commands are excluded from this flight image to provide that margin.
Do not wire a USB-UART adapter to CN10 D0/D1 while the current firmware still selects PG9/PG14. The UART can be functioning correctly in software while no signal reaches those Arduino pins.

3. Physical connection

The supplied PDF is for a different board. ../um3.pdf identifies itself as UM3115 for NUCLEO-H563ZI (MB1404), not NUCLEO-H753ZI (MB1364). Its LPUART1 solder-bridge designators and jumper settings must not be applied to this target. The H753ZI source of truth is ST UM2407.

USART6 wiring

For the signal-level drawing that includes MCU alternate functions, Morpho pins, crossed directions, unused adapter pins, power sequencing, and the separate console path, see the detailed USART6 connection diagram in the test runbook.

MCU signalBoard locationUSB-UART connection
PG14 / USART6 TXCN12 Morpho pin 61Adapter RX
PG9 / USART6 RXCN11 Morpho pin 63Adapter TX
GroundCN12 Morpho pin 63, or another GNDAdapter GND
  • Use 3.3 V TTL logic.
  • Do not connect the adapter's VCC or 5 V wire.
  • Power the Nucleo through CN1 ST-LINK USB.
  • Use a short cable and an adapter known to sustain 921600 baud.
  • Cross TX and RX: board TX to adapter RX, board RX to adapter TX.

Stock MB1364 jumper and solder-bridge state

USART6 PG9 / PG14No bridge changeUse CN11-63 and CN12-61 directly. The PG9/PG14 names in UM2407's SB12/SB19 description refer to pins on the ST-LINK STM32F723, not the target STM32H753.

The pin assignments are defined by nuttx-config/include/board.h and can be verified against ST's UM2407 Nucleo-144 user manual.

Stable Linux device names

Do not assume that the first device will always be /dev/ttyACM0:

ls -l /dev/serial/by-id/
udevadm info --query=all --name=/dev/ttyUSB0

Prefer a /dev/serial/by-id/... path in scripts. The complete setup can expose one ACM device from ST-LINK, another from CN13, and one USB device from the UART adapter.

4. NuttX setup

The current NSH defconfig already enables:

CONFIG_STM32H7_USART3=y
CONFIG_STM32H7_USART6=y
CONFIG_STM32H7_SERIAL_DISABLE_REORDERING=y
CONFIG_USART3_SERIAL_CONSOLE=y
CONFIG_USART6_BAUD=921600
CONFIG_USART6_RXBUFSIZE=512
CONFIG_USART6_TXBUFSIZE=512

USART6 defaults to 921600 baud to match the dedicated DDS link. The DDS client also requests that speed with termios when started with -b 921600.

Start with the existing 512-byte NuttX buffers. If measurements show overrun or packet loss under high-rate traffic, increase them to 1024 or 2048 bytes and re-check RAM usage. Hardware flow control is not part of the three-wire connection and should remain disabled.

5. PX4 firmware setup

Implemented firmware configuration

The following is enabled in default.px4board:

CONFIG_MODULES_UXRCE_DDS_CLIENT=y

Build, inspect size, and flash:

make st_nucleo-h753zi_default
arm-none-eabi-size build/st_nucleo-h753zi_default/st_nucleo-h753zi_default.elf
make st_nucleo-h753zi_default upload

The generated serial startup owns TEL1 automatically. For isolated debugging it can be stopped and started manually from the CN1 NSH console:

uxrce_dds_client start -t serial -d /dev/ttyS1 -b 921600
uxrce_dds_client status

Manual startup is recommended until pin routing, the agent, and bidirectional traffic have been verified independently.

Parameter-driven startup

For normal PX4 serial-port integration, also add:

CONFIG_BOARD_SERIAL_TEL1="/dev/ttyS1"

Then set board defaults before rc.serial runs:

param set-default MAV_0_CONFIG 0
param set-default UXRCE_DDS_CFG 101
param set-default SER_TEL1_BAUD 921600
param set-default UXRCE_DDS_DOM_ID 0
param set-default UXRCE_DDS_KEY 1
param set-default UXRCE_DDS_SYNCT 1

UXRCE_DDS_CFG=101 assigns the DDS client to TEL1. MAVLink must not be assigned to the same port. The existing board defaults already disable its generated MAVLink serial instances because CN13 is managed separately by cdcacm_autostart.

Available topics

The compiled bridge is generated from src/modules/uxrce_dds_client/dds_topics.yaml. Entries under publications flow from PX4 to ROS 2. Entries under subscriptions flow from ROS 2 to PX4.

6. ROS 2 host setup

PX4 currently recommends Ubuntu 22.04 with ROS 2 Humble. Install ROS using the official Humble instructions, then install workspace tools and serial access: 

sudo apt update
sudo apt install ros-humble-ros-base ros-dev-tools \
  python3-colcon-common-extensions python3-rosdep python3-vcstool
sudo usermod -aG dialout "$USER"

Log out and back in after adding the user to dialout.

Micro XRCE-DDS Agent

For ROS 2 Humble, use a v2 client/agent combination. The current PX4 compatibility table specifies agent v2.4.2 for Humble: 

mkdir -p ~/src
cd ~/src
git clone -b v2.4.2 https://github.com/eProsima/Micro-XRCE-DDS-Agent.git
cd Micro-XRCE-DDS-Agent
mkdir build && cd build
cmake ..
make -j"$(nproc)"
sudo make install
sudo ldconfig

Start the serial agent:

MicroXRCEAgent serial \
  --dev /dev/serial/by-id/<usb-uart-adapter> \
  -b 921600

Do not pair the default PX4 v2 client with a v3 agent. The version selection table and current installation commands are maintained in the PX4 uXRCE-DDS guide.

8. Data flow inside PX4

PX4 to ROS 2

PX4 application / EKF2
  → orb_publish()
  → uORB DeviceNode
  → uxrce_dds_client uORB subscription and poll()
  → orb_copy()
  → generated ucdr serialization
  → Micro XRCE-DDS serial framing
  → NuttX write(/dev/ttyS1)
  → USART6 PG14
  → USB-UART adapter
  → MicroXRCEAgent
  → Fast DDS / ROS 2 graph
  → rclpy or rclcpp subscription callback

ROS 2 to PX4

ROS 2 publisher
  → ROS middleware / Fast DDS
  → MicroXRCEAgent
  → XRCE serial framing
  → USB-UART adapter
  → USART6 PG9
  → NuttX read(/dev/ttyS1)
  → uxrce_dds_client session callback
  → generated ucdr deserialization
  → uORB::Publication
      → PX4 application subscription

Outbound topic objects are uORB subscriptions inside the generated SendTopicsSubs class. Inbound topic objects are uORB publications inside RcvTopicsPubs. The agent does not know or link against PX4 application code; it creates DDS entities requested by the flight-controller client.

QoS and timestamps

  • PX4 data writers use best-effort reliability and transient-local durability.
  • PX4 data readers use best-effort reliability and volatile durability.
  • ROS subscribers should use a sensor-data-compatible best-effort profile.
  • UXRCE_DDS_SYNCT=1 compensates PX4/agent timestamp offset.
  • Best-effort topics can lose samples; flight commands should not depend on one packet.

9. MAVROS versus direct uXRCE-DDS

MAVROS can run as a ROS 2 node, but it does not make PX4 a ROS 2 participant. A PX4 application cannot subscribe directly to a MAVROS topic name. MAVROS owns the ROS-facing topic, converts its data to a defined MAVLink message, and sends that message to PX4. PX4's mavlink_receiver decodes it and publishes one or more uORB topics. The PX4 application subscribes only to those uORB topics.

Concrete MAVROS example

ROS 2 /mavros/setpoint_position/local (geometry_msgs/PoseStamped)
  → MAVROS setpoint-position plugin
  → MAVLink SET_POSITION_TARGET_LOCAL_NED
  → PX4 MavlinkReceiver::handle_message_set_position_target_local_ned()
  → offboard_control_mode and trajectory_setpoint uORB publications
  → PX4 controllers or another PX4 uORB subscriber

The PX4 conversion is implemented in src/modules/mavlink/mavlink_receiver.cpp. The handler validates the target system/component and coordinate frame, converts the MAVLink fields, and publishes uORB. The original ROS 2 topic name is not transmitted to the flight controller. 

#include <uORB/Subscription.hpp>
#include <uORB/topics/trajectory_setpoint.h>

uORB::Subscription setpoint_sub{ORB_ID(trajectory_setpoint)};
trajectory_setpoint_s setpoint{};

if (setpoint_sub.update(&setpoint)) {
    // Consume the uORB data produced from the received MAVLink message.
}

Can an arbitrary ROS 2 topic reach a PX4 application through MAVROS?

Not automatically. A topic such as /my/custom/topic reaches PX4 through MAVROS only when an explicit mapping exists. The mapping must define the ROS message, MAVLink message, coordinate/unit conversions, and destination uORB topic.

RequirementHost workPX4 workWhen to use
Existing MAVROS interface Publish or subscribe to the documented MAVROS ROS 2 topic/service. Subscribe to the uORB topic already produced by mavlink_receiver, or publish the uORB source used by an existing MAVLink stream. Use for standard MAVLink capabilities and compatibility with existing MAVROS applications.
New MAVROS interface Add a MAVROS plugin that subscribes to the ROS 2 topic and encodes a standard or custom MAVLink message. Add the MAVLink dialect/message when necessary, decode it, validate it, and publish a defined uORB topic. Use only when the data must also be represented as MAVLink.
New direct DDS interface Publish a matching px4_msgs type under /fmu/in/.... Add the PX4 message and a subscriptions entry in dds_topics.yaml; the generated bridge publishes uORB. Recommended for a new ROS 2-specific application on this board.

Reverse direction

PX4-to-ROS follows the same boundary in reverse. A PX4 application publishes uORB; a configured PX4 MAVLink stream encodes it; MAVROS receives the MAVLink message and a plugin publishes a ROS 2 topic. With direct DDS, the generated uxrce_dds_client subscription serializes the selected uORB topic directly as its corresponding px4_msgs DDS type.

Decision for Nucleo-H753ZI: keep MAVLink on CN13 for QGroundControl and HITL, and keep ROS 2 application data on uXRCE-DDS over USART6. PX4 applications remain transport-independent uORB publishers/subscribers, while new ROS 2-specific topics avoid a custom MAVROS plugin and a second MAVLink-to-uORB conversion layer.

10. End-to-end test plan

Stage 1: firmware and UART

  1. Open the CN1 NSH console at 57600 baud using its by-id path.
  2. Start MicroXRCEAgent on the USB-UART adapter.
  3. Start uxrce_dds_client manually on /dev/ttyS1.
  4. Run uxrce_dds_client status.

Expected PX4 state:

Running, connected
Using transport:     serial
Payload tx:          ... B/s
Payload rx:          ... B/s
timesync converged:  true

Stage 2: PX4 to ROS 2

source /opt/ros/humble/setup.bash
source ~/nucleo_px4_ros2_ws/install/setup.bash
ros2 topic list --types | sort | grep /fmu

ros2 topic echo /fmu/out/timesync_status \
  --qos-reliability best_effort \
  --qos-durability volatile

Without HITL or physical sensors, sensor_combined and odometry may have no samples or useful state. timesync_status and vehicle_status_v4 are better transport-first checks.

Stage 3: ROS 2 to PX4

Use the reference ROS 2 node to publish /fmu/in/onboard_computer_status at 1 Hz. Correct its VehicleStatus subscription to /fmu/out/vehicle_status_v4 before relying on that rate. 

boards/st/nucleo-h753zi/host/scripts/run_monitor.sh

On PX4:

listener onboard_computer_status -n 5

Updating samples prove the complete inbound path. The built-in PX4 listener command is sufficient for the first board-side test application.

Optional PX4 test module

A dedicated test module should subscribe to onboard_computer_status using the normal uORB C++ API and report sequence/timing statistics. It should not parse UART data or link ROS libraries. This keeps the transport boundary in uxrce_dds_client and tests exactly the interface production PX4 applications use.

11. Simulation tools for the ROS 2 host node

The same host application can be tested against simulated PX4 because the simulator does not replace the ROS-facing interface. PX4 still publishes and subscribes through uORB and uxrce_dds_client. SITL changes only the client-to-agent transport from the board's USART6 link to UDP port 8888.

12. HITL coexistence

The board has no installed flight sensors, so HITL is the best source of realistic data:

Simulator
  → CN13 USB MAVLink HIL_SENSOR / HIL_GPS
  → mavlink_receiver
  → sensor uORB topics
  → EKF2 and control modules
  → vehicle state uORB topics
  → uxrce_dds_client
  → USART6 / USB-UART
  → ROS 2

Reverse control flow remains:

PX4 controllers → actuator uORB topics → pwm_out_sim
  → MAVLink HIL_ACTUATOR_CONTROLS → CN13 → simulator

Keeping CN13 and USART6 separate allows the ROS 2 machine to observe estimator and controller behavior executing on the physical MCU without interfering with the simulator's high-rate MAVLink sensor stream.

13. Capacity and reliability considerations

Flash

The linker currently gives the application 1408 KiB from 0x08020000; four 128 KiB sectors at the end of flash are reserved for the parameter LittleFS volume. The observed non-DDS firmware is already close to this limit.

If DDS does not fit, use these remedies in order:

  1. Reduce dds_topics.yaml to the topics actually needed by the target.
  2. Create a dedicated ROS 2 board variant and disable unused PX4 modules.
  3. Only after analysis, reduce the LittleFS reservation from four to at least two erase blocks, coordinating the linker length, PARAM_LITTLEFS_ERASE_BLOCKS, and a parameter-storage migration or reformat.

Bandwidth

A 921600-baud 8-N-1 UART has a theoretical payload ceiling near 92 kB/s before XRCE framing. High-rate IMU plus odometry, attitude, and status topics can approach practical limits. Rate limits are defined in dds_topics.yaml; start with a narrow topic set and measure Payload tx/rx in the client status.

  • Short wiring and a high-quality adapter matter at 921600 baud.
  • Do not enable hardware flow control without RTS/CTS pin routing and a compatible agent.
  • Use unique nonzero UXRCE_DDS_KEY values for multiple clients.
  • Match ROS_DOMAIN_ID with UXRCE_DDS_DOM_ID.
  • Use namespaces such as uav_0 for multi-vehicle systems.

15. Phased implementation plan

Implementation should proceed through transport, firmware-capacity, bidirectional-data, and HITL gates before any ROS 2 flight command is enabled. Each phase below has an explicit completion criterion so that failures remain local and diagnosable.

  1. Enabled CONFIG_MODULES_UXRCE_DDS_CLIENT=y in the default target and removed test-only command linkage. The measured image occupies 93.56% of its flash region.
  2. Added CONFIG_BOARD_SERIAL_TEL1="/dev/ttyS1" so PX4's generated serial configuration owns the dedicated USART6 port.

  6. Added host setup, agent, and monitor scripts with stable-device guidance and static source validation that does not require ROS on the PX4 build machine.
