PX4 Architecture Review

Driver Implementation Patterns in src/drivers

This document summarizes recurring PX4 driver implementation patterns and explains how the same ideas can be adapted for autonomous driving software. It uses one input driver example, SRF02, and one output driver example, PWMOut.

Executive Summary

Core Finding

PX4 drivers are implemented as small runtime modules with explicit lifecycle commands, deterministic scheduling, hardware bus abstraction, device identity, health counters, and publish/subscribe isolation through uORB.

This creates a clean boundary between hardware acquisition/output and higher-level estimation, control, navigation, and mission logic.

Best Reuse Candidate

A self-driving project can reuse the architectural pattern, not the exact aviation semantics. The most valuable pattern is: 

driver module
  -> scheduled nonblocking hardware work
  -> typed normalized message
  -> health and timing metadata
  -> asynchronous consumers

Practical interpretation

PX4 drivers are not just thin hardware wrappers. They are supervised runtime modules that own probing, scheduling, data conversion, publication, status reporting, and shutdown. This is directly relevant to automotive sensors and actuators such as IMUs, ultrasonic sensors, radars, lidars, cameras, steering controllers, brake controllers, and power devices.

General PX4 Driver Architecture

PX4 drivers generally sit below estimators/controllers and above board-specific hardware functions. Input drivers acquire measurements and publish uORB topics. Output drivers consume control or actuator topics, apply output logic, and write to physical hardware.

physical hardware driver ownership message boundary board or platform APIs

Common Module Shape

Most drivers are compiled as PX4 modules using px4_add_module. A driver has a MAIN name, source files, dependencies, and sometimes a module.yaml configuration file for parameters. 

px4_add_module(
  MODULE drivers__distance_sensor__srf02
  MAIN srf02
  SRCS SRF02.cpp SRF02.hpp srf02_main.cpp
  DEPENDS drivers_rangefinder px4_work_queue
)

I2C/SPI Driver Framework

For I2C and SPI sensors, PX4 provides a reusable framework around I2CSPIDriver. The framework centralizes bus parsing, instance enumeration, work queue selection, startup, shutdown, and status reporting.

Example 1: Input Driver, SRF02 Rangefinder

SRF02 is a compact example of the PX4 input sensor pattern. It is an I2C ultrasonic distance sensor driver located under src/drivers/distance_sensor/srf02.

Source Files

  • SRF02.hpp: class declaration, constants, driver members.
  • SRF02.cpp: init, measure, collect, scheduling, status.
  • srf02_main.cpp: CLI entry point and lifecycle verbs.
  • CMakeLists.txt: PX4 module build declaration.

Key Design Traits

  • Inherits device::I2C for bus IO.
  • Inherits I2CSPIDriver<SRF02> for lifecycle and work queue integration.
  • Uses PX4Rangefinder to publish distance_sensor samples.
  • Uses perf counters for sample timing and communication errors.

Class Shape

class SRF02 : public device::I2C, public I2CSPIDriver<SRF02>
{
public:
  int init() override;
  void print_status() override;
  void RunImpl();

private:
  void start();
  int collect();
  int measure();
  PX4Rangefinder _px4_rangefinder;
};

Lifecycle Flow

The driver CLI creates BusCLIArguments, sets default I2C address and rotation, creates a BusInstanceIterator, then dispatches start, stop, or status to the common I2CSPIDriver methods.

What The Driver Owns

Responsibility SRF02 Implementation Architectural Benefit
Hardware probing init() calls I2C::init() before starting the cycle. Driver startup fails early if the device is not reachable.
Acquisition timing start() and RunImpl() schedule delayed execution. The sensor conversion delay is handled inside the driver, not by consumers.
Measurement command measure() writes the range command over I2C. Hardware protocol details remain hidden below the message interface.
Data conversion collect() reads two bytes, converts centimeters to meters. Consumers receive normalized SI-unit values.
Publication _px4_rangefinder.update(timestamp_sample, distance_m). Consumers subscribe to a common distance sensor topic.
Diagnostics _sample_perf, _comms_errors, print_status(). Runtime health and timing can be inspected without a debugger.

Input driver takeaway

The driver does not expose a synchronous getDistance() API to the rest of the system. It periodically acquires data, timestamps it, normalizes it, and publishes it. This prevents estimator or control logic from blocking on hardware IO.

Example 2: Output Driver, PWMOut

PWMOut is an output driver under src/drivers/pwm_out. It shows the PX4 pattern for translating actuator intent into physical PWM outputs while using the shared mixer/output framework.

Source Files

  • PWMOut.hpp: module class, output interface, parameters.
  • PWMOut.cpp: scheduling, PWM init, output writes.
  • CMakeLists.txt: module declaration and module.yaml.
  • mixer_module.hpp: OutputModuleInterface and MixingOutput.

Key Design Traits

  • Inherits ModuleBase for module lifecycle.
  • Inherits OutputModuleInterface for scheduled output execution.
  • Uses MixingOutput to handle actuator subscriptions and output functions.
  • Writes hardware with board-level PWM APIs such as up_pwm_servo_set().

Class Shape

class PWMOut final : public ModuleBase, public OutputModuleInterface
{
public:
  static int task_spawn(int argc, char *argv[]);
  int print_status() override;
  bool updateOutputs(float outputs[MAX_ACTUATORS],
                     unsigned num_outputs,
                     unsigned num_control_groups_updated) override;

private:
  void Run() override;
  void update_params();
  bool update_pwm_out_state(bool on);
  MixingOutput _mixing_output;
};

Output Flow

PWMOut is scheduled as a work queue module. Its Run() method calls _mixing_output.update(). The mixer module processes actuator controls, output functions, arming/disarming rules, min/max/failsafe values, and then calls the driver's updateOutputs() callback. The driver writes final PWM values to hardware.

What The Driver Owns

Responsibility PWMOut Implementation Architectural Benefit
Module spawn task_spawn() creates the driver instance and schedules it. Output driver lifecycle is managed like other PX4 runtime modules.
Output scheduling OutputModuleInterface runs on hp_default work queue. Actuator writes run in a high-priority scheduled context.
Actuator mediation MixingOutput handles subscriptions, mixing, output functions, and limits. Driver is not responsible for high-level control allocation policy.
Hardware initialization update_pwm_out_state() initializes PWM timers, rates, and masks. Board-specific timer details stay below the output abstraction.
Physical write updateOutputs() calls up_pwm_servo_set() and up_pwm_update(). Only final bounded outputs reach hardware pins.
Parameter handling parameter_update subscription triggers update_params(). Runtime configuration changes are reflected without direct consumer coupling.

Output driver takeaway

PX4 output drivers do not let every controller write directly to hardware. Control intent goes through a mediation layer that handles function assignment, limits, failsafe values, arming state, and hardware-specific output details.

Implementation Patterns To Copy

1. Keep IO Local

Hardware-specific protocol code stays inside the driver. Consumers should not know register addresses, bus commands, timer groups, or file descriptors.

2. Publish Normalized Data

Drivers convert hardware units into system units before publication. The SRF02 driver converts centimeters into meters before publishing distance.

3. Schedule, Do Not Block

Drivers run short work queue callbacks and reschedule themselves. Long blocking calls should not run in a shared high-priority driver path.

4. Separate Policy From IO

Output policy is handled by MixingOutput, while PWMOut performs final hardware writes. This keeps actuator rules separate from the board driver.

5. Add Runtime Diagnostics

Every serious driver should expose timing and communication health. PX4 uses perf counters and print_status() consistently.

6. Preserve Device Identity

Device ID and bus metadata allow calibration, voting, fault isolation, and field debugging to remain tied to the physical device.

Suggested Generic Driver Skeleton

class MySensor final : public device::I2C, public I2CSPIDriver<MySensor>
{
public:
  int init() override
  {
    if (I2C::init() != PX4_OK) {
      return PX4_ERROR;
    }

    ScheduleDelayed(first_sample_delay_us);
    return PX4_OK;
  }

  void RunImpl()
  {
    const hrt_abstime sample_time = hrt_absolute_time();

    if (read_hardware_sample(sample_time) == PX4_OK) {
      publish_normalized_sample(sample_time);
    } else {
      perf_count(_comms_errors);
    }

    ScheduleDelayed(sample_period_us);
  }

  void print_status() override
  {
    I2CSPIDriverBase::print_status();
    perf_print_counter(_comms_errors);
  }
};

Suggested Generic Output Skeleton

class MyActuatorOutput final : public ModuleBase, public OutputModuleInterface
{
private:
  void Run() override
  {
    if (should_exit()) {
      ScheduleClear();
      exit_and_cleanup(desc);
      return;
    }

    _output_mediator.update();
    check_parameter_updates();
    _output_mediator.updateSubscriptions(true);
  }

  bool updateOutputs(float outputs[MAX_ACTUATORS],
                     unsigned num_outputs,
                     unsigned updated_groups) override
  {
    for (unsigned i = 0; i < num_outputs; ++i) {
      write_bounded_output_to_hardware(i, outputs[i]);
    }

    trigger_hardware_update_if_needed(updated_groups);
    return true;
  }
};

How This Applies To Self-Driving Software

A self-driving stack usually has more complex sensors and more complex compute than PX4, but the low-level architecture pattern remains useful. The pattern is especially valuable for ultrasonic sensors, radars, IMUs, wheel speed sensors, GNSS receivers, steering/brake command interfaces, power monitors, and vehicle network gateways.

Recommended Automotive Mapping

PX4 Concept Automotive Mapping Why It Helps
I2CSPIDriver bus framework Device registry for CAN, SOME/IP, Ethernet, PCIe, SPI, and serial devices. Consistent startup, discovery, and diagnostic behavior across heterogeneous hardware.
ScheduledWorkItem Deterministic executor or real-time callback group. Bounds runtime behavior and avoids unstructured blocking in drivers.
PX4Rangefinder wrapper Sensor-specific message adapter with timestamp, frame, calibration, health. Separates hardware protocol from perception/fusion contracts.
MixingOutput Actuator command mediator for steering, brake, throttle, and gear requests. Centralizes arbitration, saturation, state gating, and failsafe behavior.
print_status() and perf counters Driver health endpoint and telemetry stream. Improves serviceability, field debugging, and automated health monitoring.
uORB topics DDS/ROS 2/iceoryx/vehicle middleware topics. Creates a stable asynchronous interface between drivers and algorithms.

Do not copy PX4 blindly

Automotive autonomy has different safety, security, bandwidth, timing, and lifecycle requirements. PX4's implementation patterns are useful, but a self-driving system still needs ISO 26262 work products, cybersecurity engineering, secure boot/update policy, threat analysis, real-time budget evidence, and vehicle-specific fault handling.

Checklist For A PX4-Inspired Driver Layer

Area Checklist Item Status Target
Lifecycle Every driver has explicit start, stop, status, and restart behavior. Required
Scheduling Driver IO is scheduled and bounded; long blocking calls are isolated. Required
Message contract Driver publishes or consumes typed normalized messages, not ad hoc APIs. Required
Identity Every physical device has stable identity, bus metadata, and calibration linkage. Required
Diagnostics Expose communication errors, sample latency, stale data, and driver state. Required
Safety Define timeout behavior, invalid data handling, degraded mode, and safe output state. Required for safety-relevant devices
Security Authenticate update/config paths, restrict debug interfaces, and log privileged actions. Required for production vehicles
Verification Unit tests, SIL/HIL tests, fault injection, bus error tests, and timing tests exist. Required
