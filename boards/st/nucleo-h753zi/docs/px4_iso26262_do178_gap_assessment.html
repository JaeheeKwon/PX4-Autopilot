Safety Standards Gap Assessment

PX4 Gaps Against ISO 26262 and DO-178C

PX4 has strong architectural mechanisms for modular control, typed messages, failsafe handling, logging, and replay. Those mechanisms are useful inputs to a safety argument, but they are not the lifecycle evidence required for ISO 26262 automotive functional safety or DO-178C airborne software assurance.

Repository: PX4-Autopilot Scope: architecture and evidence gap review Prepared: 2026-06-22

Executive Summary

Primary finding: PX4 provides useful safety-related mechanisms, but it does not provide a certification-ready safety case for ISO 26262 or DO-178C. The largest gaps are hazard analysis, requirements traceability, independence, qualified verification, tool qualification, configuration control, and lifecycle work products.

ISO 26262 is an automotive functional safety standard for safety-related electrical and electronic systems in road vehicles. DO-178C is an aviation software assurance standard used as an acceptable means of compliance for airborne software. Both standards require explicit lifecycle evidence. A good architecture is necessary, but it is not sufficient.

PX4 should be treated as a reference architecture for a deterministic control supervisor, not as a compliant baseline. A project that wants ISO 26262 or DO-178C alignment would need to add the standards process around the software, then rework or constrain parts of the architecture where evidence cannot be produced.

What PX4 Already Helps With

Modular Components

PX4 modules and work queues create a clear runtime structure that can support allocation of responsibilities.

Typed Interfaces

uORB messages provide explicit data contracts that can become interface-control artifacts.

Health and Failsafe

Commander, health reports, and failsafe flags provide a practical pattern for mode gating and degraded behavior.

Log and Replay

Topic logging and replay can support regression testing, tuning, and failure reproduction.

Parameterization

Parameters support platform variation and calibration, but would need stronger configuration control.

Simulation Hooks

SITL and HITL support validation loops, but certification credit would require qualified environments and test evidence.

Hardware random failures Major gap PX4 software architecture does not provide SPFM, LFM, PMHF, FMEDA, or diagnostic coverage for target hardware. FMEDA, safety manual integration, diagnostic coverage evidence, hardware-software interface assumptions.
Software safety requirements Major gap Source files and documentation are not organized as ASIL-specific software safety requirements. Software safety requirements, architectural design, unit design, safety analyses, verification criteria.
Traceability Major gap No bidirectional trace from hazard to safety goal, requirement, architecture, code, unit test, integration test, and validation result. Requirements database, trace matrix, verification coverage reports, change impact analysis.
Tool qualification Major gap Compilers, message generators, build scripts, simulators, log tools, and coverage tools are not qualified for safety credit. Tool classification, tool qualification plan, validation evidence, usage constraints, tool confidence argument.

Production, operation, service Major gap Open-source project structure does not define production release, service, decommissioning, or field monitoring responsibilities. Production safety plan, service instructions, anomaly handling, recall/update process, safety monitoring.

Requirements-based testing Partial PX4 has tests, SITL, and replay, but tests are not organized as complete normal-range and robustness tests against requirements. Requirements-based test cases, procedures, expected results, pass/fail records, robustness test evidence.
Structural coverage Major gap No DAL-specific statement, decision, or MC/DC coverage evidence. Coverage analysis, coverage closure, justification of uncovered code, additional tests or code removal.
Data and control coupling Partial uORB helps expose data flow, but no certification analysis of data coupling and control coupling is present. Interface design, coupling analysis, integration tests demonstrating coupling behavior.
Dead and deactivated code Major gap Large configurable codebase contains many build variants and optional paths with no DO-178C-style dead/deactivated code argument. Code reachability analysis, deactivated code rationale, configuration-specific code inventory.

Important Architectural Risks

  • Shared address space: PX4's runtime model is efficient, but safety standards often require stronger freedom-from-interference arguments for memory, timing, and resources.
  • Parameter-heavy behavior: Parameters are useful, but safety-critical parameter data must be classified, range-controlled, verified, and released under configuration control.
  • Generated interfaces: .msg files and generated topic code are powerful, but generators and generated outputs become part of the assurance argument.
  • Open-source change velocity: Rapid upstream evolution conflicts with certification baselines unless a controlled fork, change impact process, and release authority are established.
  • Simulation credit: SITL, HITL, and replay are valuable engineering tools, but they do not automatically count as qualified verification environments.

Recommended Compliance-Oriented Path

  1. Define the target product, vehicle role, ODD, safety boundary, and operational assumptions before adapting PX4 concepts.
  2. Perform HARA or aircraft/system safety assessment first. Let safety goals or failure-condition classifications drive architecture, not the other way around.
  3. Create safety requirements and traceability before code changes. Use PX4 modules and topics as allocation targets.
  4. Partition safety-critical control from non-critical telemetry, logging, simulation, and developer tooling.
  5. Establish coding standards, static analysis, unit verification, integration verification, and coverage closure appropriate to ASIL or DAL.
  6. Classify tools and generated code. Decide which tools are used only for engineering convenience and which are credited for safety evidence.
  7. Freeze a controlled baseline. Treat upstream PX4 updates as supplier inputs requiring impact analysis and re-verification.

Bottom Line

PX4 is a useful architectural reference for a safety-aware control runtime, but it is not an ISO 26262 or DO-178C compliant software baseline by default. Its best assets are modularity, typed topics, centralized health/failsafe handling, logging, replay, and simulation support. Its missing pieces are the formal safety lifecycle, requirements structure, independent verification, traceability, tool qualification, hardware safety analysis, and controlled production process.

For a self-driving project, the right use is selective: borrow the control-supervisor pattern, then build an ISO 26262 safety case around a constrained and controlled implementation. For an aviation project, DO-178C requires a separate airborne software assurance program from the beginning.
