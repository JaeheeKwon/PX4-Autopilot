MPU and NuttX Protected Build Exploration

This document describes how to explore memory protection on the ST Nucleo-H753ZI PX4 target using the ARM Cortex-M7 MPU and NuttX protected build mode.

The goal is fault containment: move selected PX4 modules into unprivileged user space so they cannot directly access protected kernel memory or hardware registers. This is useful for functional-safety exploration, but it is not a complete safety argument by itself.

The markdown source for this page is mpu_nuttx_protected_build.md.

Summary

PX4 on NuttX normally runs as a flat firmware image. In a flat build, modules, drivers, middleware, and startup code share the same privilege level and address space.

NuttX protected build changes that model:

flowchart LR subgraph flash["Firmware image"] kernel["Kernel blob<br/>privileged"] user["User blob<br/>unprivileged"] end subgraph kernel_side["Kernel side"] drivers["Hardware drivers"] critical["Critical PX4 modules"] kernel_uorb["uORB kernel interface"] end subgraph user_side["User side"] app["Less-trusted PX4 module"] user_uorb["uORB user interface"] end mpu["ARMv7-M MPU<br/>region permissions"] kernel --> kernel_side user --> user_side mpu --> kernel mpu --> user app -- "syscalls / file descriptors / ioctl / uORB" --> kernel_side

The practical result is a two-domain split:

DomainPrivilegeTypical contents
Kernel spacePrivilegedNuttX kernel, low-level board code, hardware drivers, safety-critical PX4 modules.
User spaceUnprivilegedSelected PX4 modules and system commands that should not directly touch kernel memory or peripherals.

This is not per-module address-space isolation. User-space modules still share the user-space blob and user heap, so one user module can still corrupt another user module. The MPU boundary is mainly between privileged kernel space and unprivileged user space.

Current Nucleo-H753ZI State

The current st_nucleo-h753zi_default target is a flat NuttX build.

AreaCurrent state

NuttX configboards/st/nucleo-h753zi/nuttx-config/nsh/defconfig does not enable CONFIG_BUILD_PROTECTED.
MPUCONFIG_ARM_MPU_EARLY_RESET=y is present, but protected user/kernel separation is not enabled.

Because of that, MPU-backed user/kernel isolation is an exploration item for this board, not a drop-in production feature.

PX4 and NuttX Switches

NuttX protected build

NuttX creates the protected execution model with:

CONFIG_BUILD_PROTECTED=y
CONFIG_ARM_MPU=y
CONFIG_NUTTX_USERSPACE=<user_flash_start>

CONFIG_BUILD_PROTECTED=y builds NuttX and selected applications as two separately linked objects:

ObjectPurpose
Kernel blobPrivileged code and kernel data.
User blobUnprivileged code and user data.

CONFIG_NUTTX_USERSPACE must match the start address of the user-space blob in the protected linker layout.

PX4 module placement

PX4 enables its module-placement logic with:

CONFIG_BOARD_PROTECTED=y

For each module, PX4 then uses CONFIG_USER_<MODULE> to decide whether the module should be linked into user space.

CONFIG_MODULES_MY_AUTO_WP=y
CONFIG_USER_MY_AUTO_WP=y
  • Enabled modules with CONFIG_USER_<MODULE>=y are linked into user space.
  • Enabled modules without a user-space marker are linked into kernel space.
  • Kernel-side modules link against kernel-facing PX4 interfaces such as px4_kernel_layer and uORB_kernel.
  • User-side modules link against user-facing PX4 interfaces such as px4_layer and normal uORB.

Add User-Space Selection to a Custom Module

For a custom module in:

src/modules/my_auto_wp/

add both the normal module symbol and the protected-build user-space symbol to src/modules/my_auto_wp/Kconfig:

menuconfig MODULES_MY_AUTO_WP
	bool "my_auto_wp"
	default n
	---help---
		Enable my_auto_wp

menuconfig USER_MY_AUTO_WP
	bool "my_auto_wp running as userspace module"
	default y
	depends on BOARD_PROTECTED && MODULES_MY_AUTO_WP
	---help---
		Put my_auto_wp in userspace memory

Use default y for modules that should normally move to user space when a protected board build is selected. Use default n when the module should remain kernel-side unless explicitly requested.

Create a Protected Board Variant

Use a separate variant instead of changing the default board image.

boards/st/nucleo-h753zi/protected.px4board

For non-default PX4 board labels, the build merges default.px4board with the variant .px4board, so the variant should contain only the differences:

CONFIG_BOARD_PROTECTED=y
CONFIG_MODULES_MY_AUTO_WP=y
CONFIG_USER_MY_AUTO_WP=y

Build target:

make st_nucleo-h753zi_protected

PX4 chooses the NuttX config directory by board label. Because the label is protected, the build expects:

boards/st/nucleo-h753zi/nuttx-config/protected/defconfig

If that directory does not exist, PX4 falls back to the normal nsh NuttX config, which is not sufficient for a protected build.

Create the Protected NuttX Config

Start from the current Nucleo-H753ZI nsh defconfig, then enable the protected build options through menuconfig or defconfig generation.

CONFIG_EXPERIMENTAL=y
CONFIG_BUILD_PROTECTED=y
CONFIG_ARM_MPU=y
CONFIG_ARM_MPU_EARLY_RESET=y
CONFIG_ARM_MPU_NREGIONS=8
CONFIG_NUTTX_USERSPACE=<user_flash_start>
CONFIG_MM_KERNEL_HEAP=y
CONFIG_MM_KERNEL_HEAPSIZE=<kernel_heap_bytes>

The existing FMU-v5 protected target is the closest PX4 reference:

boards/px4/fmu-v5/protected.px4board
boards/px4/fmu-v5/nuttx-config/protected/defconfig
boards/px4/fmu-v5/nuttx-config/scripts/memory.ld
boards/px4/fmu-v5/nuttx-config/scripts/kernel-space.ld
boards/px4/fmu-v5/nuttx-config/scripts/user-space.ld

Do not copy those addresses directly. They are for STM32F7, not STM32H753.

Protected Linker Layout

The current Nucleo-H753ZI linker script uses one application flash region and one main application RAM region. A protected build needs a split layout.

kflash  privileged text/rodata
uflash  unprivileged text/rodata/userspace header

ksram   privileged data/bss/kernel heap
usram   unprivileged data/bss/user heap
ScriptPurpose
memory.ldDefines kflash, uflash, ksram, usram, and any extra RAM regions.
kernel-space.ldPlaces vectors and privileged kernel sections into kernel regions.
user-space.ldPlaces the userspace header and user sections into user regions.

The user flash start in memory.ld must match CONFIG_NUTTX_USERSPACE.

RegionExisting constraint
0x08000000 to 0x0801ffffPX4 bootloader area.
0x08020000 onwardApplication firmware starts here in the current flat image.
Upper flash sectorsReserved by the current board layout for LittleFS/parameter storage.

Use flash-sector-aligned boundaries. Do not place user flash over the bootloader or the LittleFS parameter sectors.

Runtime Access Model

A user-space PX4 module should access the system through existing OS and PX4 interfaces:

NeedPreferred access path
Publish or subscribe datauORB
Read parametersPX4 parameter API
Use a hardware deviceFile descriptor, driver API, or ioctl exposed by a kernel-side driver
Send diagnosticsevents, logging, or mavlink-facing APIs
Request mode changescommander-facing APIs or published command topics

Avoid direct register access and raw kernel pointer sharing in user-space modules. If a user-space module needs hardware access, keep the hardware driver kernel-side and expose a narrow checked interface.

Validation Plan

Build-time checks

  1. Confirm build/st_nucleo-h753zi_protected/boardconfig contains CONFIG_BOARD_PROTECTED=y.
  2. Confirm the NuttX .config contains CONFIG_BUILD_PROTECTED=y.
  3. Confirm the user-space module appears as CONFIG_USER_MY_AUTO_WP=y.
  4. Inspect generated map files and symbols to verify the module is linked into the user blob, not the kernel blob.

Runtime positive tests

  1. Boot the board and confirm the normal shell still starts.
  2. Start the user-space module:
my_auto_wp start
my_auto_wp status
  1. Verify normal uORB publish/subscribe behavior.
  2. Verify parameter reads and writes if the module uses parameters.
  3. Run the normal HITL workflow and check for timing regressions.

Runtime negative tests

Add a temporary fault-injection command to the user-space module and verify that protection triggers as expected.

FaultExpected result
Read from a kernel-only RAM addressMemory fault or controlled crash path.
Write to a kernel-only RAM addressMemory fault or controlled crash path.
Direct write to a peripheral registerMemory fault if the region is not user-accessible.
Stack overflow in user moduleDetectable failure without silent corruption of kernel data.

Record the fault, reset behavior, crash dump, and whether critical state is preserved well enough for the intended safety concept.

Functional-Safety Notes

MPU isolation is only one mechanism in a safety architecture.

LimitationImpact
User modules share user spaceMPU protection does not isolate user modules from each other.
MPU regions are limitedRegion count and alignment constraints force coarse partitions.
DMA is not constrained by the CPU MPUDrivers using DMA still need careful buffer ownership, cache management, and hardware-level controls.
Timing changesSyscalls, protected interfaces, and extra checks can affect latency and scheduling.
STM32H7 support is WIP in this treeTreat this as an engineering exploration before any safety claim.

Evidence needed for a safety argument includes hazard analysis, allocation of critical and non-critical software, interface contracts, fault-injection evidence, timing analysis, and regression tests.

Recommended Exploration Path

  1. Build and inspect an existing protected reference target such as px4_fmu-v5_protected.
  2. Add USER_MY_AUTO_WP to a custom, non-critical Nucleo module.
  3. Create st_nucleo-h753zi_protected as a separate board variant.
  4. Add a matching nuttx-config/protected config and protected linker layout.
  5. Bring up the board with only one user-space module.
  6. Add controlled memory fault tests.
  7. Move additional non-critical modules to user space only after the first module is stable.

Keep flight-critical hardware drivers and minimal safety-monitoring logic in kernel space until the protected build, interfaces, and timing are well characterized.
