PX4 Attack Surface Assessment for Self-Driving Control Runtime Use

PX4 has practical mechanisms for secure boot, MAVLink signing, module isolation by convention, and controlled topic bridging. The attack surface is still broad when the architecture is connected to radios, Ethernet, companion computers, ROS 2, CAN devices, SD-card configuration, debug ports, and drive-by-wire interfaces.

Repository: PX4-Autopilot Scope: attack surface and mitigation review Prepared: 2026-06-22

Executive Summary

Primary risk: Any unauthenticated path that can send control, shell, parameter, mission, bridge, or actuator messages can become a direct safety risk. In a self-driving adaptation, that risk maps from "flight command" to "steering, brake, throttle, gear, and mode authority."

The highest-value assets are control authority, mode authority, actuator commands, safety parameters, firmware integrity, signing keys, logs, mission or route data, and bridge topic mappings. The strongest trust boundaries are the vehicle network boundary, companion-computer boundary, CAN/drive-by-wire boundary, physical maintenance boundary, and software supply-chain boundary.

PX4's own documentation warns that unauthenticated MAVLink can allow shell commands, file operations, parameter changes, mission upload, arming, reboot, and termination. That makes communication security and topic authorization mandatory before adapting PX4 concepts into a self-driving project.

Critical Assets

Control Authority

Commands that affect steering, braking, throttle, arming, actuator output, or trajectory tracking.

Mode Authority

State-machine decisions for manual, autonomous, degraded, emergency stop, and minimal-risk maneuvers.

Configuration

Parameters, topic mappings, SD-card startup scripts, calibration files, and vehicle variant data.

Firmware Integrity

Bootloader, firmware image, module load paths, generated interfaces, and update tooling.

Credentials

MAVLink signing keys, secure boot private keys, companion credentials, network keys, and diagnostic access.

Telemetry and Logs

Location, routes, maps, event logs, fault logs, replay files, and operational behavior data.

Attack Surface Inventory

Surface Risk Possible Impact Primary Mitigations
MAVLink radio, serial, UDP, TCP High Unauthorized commands, shell access, file operations, parameter changes, mission overwrite, reboot, flight termination, or false telemetry injection. Enable MAVLink 2 signing, provision keys only on trusted links, firewall network ports, isolate radios, restrict shell/FTP in production builds, monitor rejected messages.
MAVLink signing key storage High Physical SD-card access can expose or remove the key file, disabling or bypassing trust assumptions. Lock or eliminate removable SD-card access, use tamper controls, encrypt or bind keys where platform support exists, define key rotation and revocation procedures.
ROS 2 / uXRCE-DDS bridge High Companion or network node can publish commands into PX4 topics, receive telemetry, or abuse mismatched message definitions. Use DDS security or network isolation, topic allowlists, bridge topic minimization, command freshness checks, companion hardening, version-locked message definitions.
Zenoh bridge and router High Router compromise or topic mapping changes can expose control and telemetry paths over TCP, UDP, multicast, or distributed networks. Authenticate router access, restrict peers, disable multicast where not needed, protect SD-card topic mapping files, limit subscribed control topics.
Companion computer High Compromise of Linux companion can become control-plane compromise through MAVLink, DDS, Zenoh, serial, or CAN gateways. Harden OS, least privilege, signed updates, secure boot, network firewalling, container isolation, audit services, restrict bridge credentials.
CAN / DroneCAN / UAVCAN High Spoofed sensors, fake actuator state, firmware update abuse, node ID collision, or command injection to ESCs and peripherals. Segment safety-critical CAN, authenticate gateways where possible, static node IDs for critical nodes, message plausibility checks, update authorization, bus monitoring.
Vehicle CAN and drive-by-wire adaptation High Unauthorized steering, brake, throttle, gear, park, or mode commands. Safety gateway, command authorization, rate and envelope limits, independent emergency stop, source authentication, CAN IDS, hardware interlocks.
Parameters and remote tuning High Changed failsafe thresholds, actuator limits, mode selection, controller gains, topic subscriptions, or sensor selection. Lock safety parameters, require signed/authorized changes, separate calibration mode, maintain golden configuration, log and alarm on changes.
SD-card startup and configuration High rc.txt, config.txt, or extras.txt can replace startup, modify parameters, or start extra apps. Disable SD-card startup override in production, sign configuration bundles, physical access controls, boot-time integrity checks, immutable production images.
System console, MAVLink shell, debug UART High Direct command execution, module start/stop, log inspection, parameter changes, and boot diagnostics access. Disable production shells, require authentication, physically protect debug connectors, separate development and production firmware builds.
SWD / JTAG debug ports High Firmware extraction, reflashing, memory inspection, bypass of software security, key extraction if stored in accessible memory or flash. Lock debug access, remove or seal connectors, use secure boot, use hardware key storage when available, control factory access.
Bootloader and firmware update path High Unauthorized firmware, rollback to vulnerable firmware, test-key use in production, or supply-chain insertion. Enable secure boot with production keys, protect private keys, anti-rollback policy, signed update manifests, release signing process.
Sensor inputs Medium GNSS spoofing, IMU fault injection, magnetometer disturbance, camera or rangefinder spoofing, false obstacle or position estimates. Sensor fusion consistency checks, authenticated GNSS where available, redundancy, physical shielding, plausibility monitoring, degraded-mode logic.
Logging, replay, and ULog streaming Medium Privacy leakage, route leakage, tampered evidence, storage exhaustion, or replay data used as an input source in unsafe contexts. Encrypt sensitive logs, sign logs, rotate storage, restrict log streaming, separate test replay from production runtime.
Simulation and SITL interfaces Medium Simulation ports, developer shells, dynamic modules, and test bridges can leak into production images or lab networks. Separate build variants, block simulation services in production, scan enabled modules, firewall lab networks, release-gate build configs.
Supply chain and generated code Medium Compromised dependencies, submodules, message generators, scripts, build tools, or generated topic bridges. Pinned dependencies, reproducible builds, signed source provenance, generator review, SBOM, vulnerability monitoring.

Security Strengths Present in PX4

  • MAVLink 2 signing support can authenticate incoming MAVLink commands when a key is provisioned.
  • PX4 documents production MAVLink hardening and explicitly identifies high-risk unsigned capabilities.
  • Secure boot support exists for OEM use on supported targets, using firmware signatures verified by the bootloader.
  • Health, arming checks, failsafe flags, and commander provide useful guardrails for unsafe states.
  • Topic-based architecture makes data flows easier to inventory than ad hoc direct calls.
  • Logging and event mechanisms can support incident analysis if logs are protected from tampering and leakage.

Security Gaps

PX4 gives building blocks, but the deployment security posture depends heavily on the integrator. A production vehicle needs a security architecture, not just feature switches.
  • No default end-to-end encryption for MAVLink. Signing authenticates and detects tampering, but telemetry and commands remain visible to eavesdroppers.
  • Initial MAVLink signing provisioning is accepted before a key exists, so first provisioning must be done on a trusted link.
  • Some MAVLink messages remain accepted unsigned by design, which leaves residual spoofing risk.
  • Security-critical keys and configuration can depend on removable SD-card storage.
  • ROS 2, DDS, and Zenoh bridges require separate access control and topic authorization design.
  • CAN and many embedded peripheral buses do not provide authentication by default.
  • Debug ports and system consoles can bypass higher-level security if physically accessible.
  • Simulation, dynamic modules, test shells, and developer services must be excluded from production builds.
  • No complete ISO/SAE 21434-style Threat Analysis and Risk Assessment is present for a self-driving item.

Self-Driving Specific Concerns

A self-driving adaptation changes the consequence of several PX4 surfaces. MAVLink or ROS 2 offboard control becomes a steering and braking authority path. CAN peripherals become part of drive-by-wire trust. Parameters become safety-critical calibration data. Logs and telemetry become privacy-sensitive vehicle behavior data. The bridge between autonomy compute and control runtime becomes the highest-value trust boundary.

Automotive Asset PX4-Inspired Surface Required Security Control

Recommended Mitigation Program

  1. Define assets, trust boundaries, attacker classes, and misuse cases for the actual self-driving item.
  2. Perform a TARA aligned with ISO/SAE 21434 and connect the result to the ISO 26262 safety concept.
  3. Reduce exposed interfaces: disable unused MAVLink services, shells, dynamic modules, simulation bridges, debug commands, and unused bridge topics.
  4. Require authentication for every control-authority path, including companion-to-controller, controller-to-actuator, and maintenance tools.
  5. Protect configuration integrity with signed parameter bundles, boot-time checks, and release-controlled defaults.
  6. Use secure boot and signed firmware for every production ECU and companion image. Replace test keys with production keys and define key custody.
  7. Segment networks: separate public, cloud, maintenance, autonomy compute, control, and actuator buses.
  8. Add runtime intrusion and anomaly monitoring for command rates, source identity, sensor plausibility, CAN traffic, and unexpected parameter changes.
  9. Establish vulnerability management: SBOM, dependency tracking, coordinated disclosure, patch triage, and secure update rollout.

Immediate Hardening Checklist

  • Enable MAVLink 2 signing before any wireless or network exposure.
  • Do not expose MAVLink UDP/TCP ports to untrusted networks or the internet.
  • Disable MAVLink shell and file operations in production unless explicitly required and authenticated.
  • Lock or remove external access to SD card, debug UART, SWD, and JTAG.
  • Use production secure-boot keys and remove upstream test keys from deployable builds.
  • Minimize DDS and Zenoh bridge topic sets, especially subscribed command topics.
  • Protect ROS 2 and Zenoh routers with network access control and peer authorization.
  • Use a safety gateway for vehicle CAN and drive-by-wire command paths.
  • Log security-relevant events: rejected signatures, parameter changes, mode requests, firmware version, topic map changes, and CAN anomalies.
